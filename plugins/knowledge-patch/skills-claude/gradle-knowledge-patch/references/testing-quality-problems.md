# Testing, Quality, and Problems

## Test discovery and non-class definitions

`Test` can discover definitions consumed by a custom JUnit Platform
`TestEngine` without requiring a test class (since `9.4.0`). Point
`testDefinitionDirs` at the definitions:

```kotlin
tasks.named<Test>("test") {
    testDefinitionDirs.from("src/test/definitions")
}
```

This also allows Cucumber feature files to run directly, without an empty
suite class or JUnit extension.

Projects generated by `init` use the generic
`org.jetbrains.kotlin:kotlin-test` dependency rather than
`kotlin-test-junit5` (since `9.1.0`). Its resolved test-library variant follows
the configured test runner.

## Built-in report semantics

JUnit XML test-event timestamps have millisecond precision as of `8.13.0`.
Consumers must accept values such as:

```xml
timestamp="2024-02-03T12:34:56.789"
```

When an assumption violation skips a JUnit 4, JUnit Platform, or TestNG test,
the reason appears in both HTML and JUnit XML reports (since `8.14.0`).

HTML reports reflect the testing framework hierarchy as of `9.3.0`:

- Nested classes are children of their enclosing class.
- Each parameterized method owns its invocations.
- Suites own their classes.
- Synthetic package containers are omitted.
- Standard output and error remain attributed to the test that emitted them.

Nested-class XML files keep the form `TEST-OuterClass$InnerClass.xml`. Suite
XML emits class reports only.

`TestReport` and the Test Report Aggregation Plugin preserve each input as a
separate source tab rather than merging overlapping structures (`9.3.0`).
This prevents results from identically named suites or classes in different
subprojects from becoming indistinguishable.

HTML report columns are sortable as of `9.6.1`. A click sorts, another reverses
the order, and a further interaction restores the original order. Tests,
Failures, Skipped, and Duration sort descending first; Success rate sorts
ascending first.

## JUnit data, attachments, and metadata listeners

Gradle captures JUnit Platform `TestReporter` entries and files in HTML and XML
reports (since `9.4.0`), including values emitted during construction, setup,
and teardown:

```java
testReporter.publishEntry("browser", "firefox");
testReporter.publishFile(
    "screenshot.svg",
    MediaType.create("image", "svg+xml"),
    file -> {}
);
```

HTML reports expose Data and Attachments tabs. XML maps entries into
`<properties/>` and renders file references as
`[[ATTACHMENT|/path/to/file]]`.

Build logic can consume structured metadata through
`Test.addTestMetadataListener(TestMetadataListener)` instead of parsing
standard output:

```kotlin
tasks.named<Test>("test") {
    addTestMetadataListener(LoggingListener())
}
```

## Reports for tests outside Gradle's test infrastructure

Plugin and platform authors can inject `TestEventReporterFactory` to create
Gradle-style binary results and HTML reports for externally executed tests
(since `8.13.0`). A reporter can add timestamped metadata and nest
`reportTestGroup(...)` and `reportTest(...)` events.

```java
try (TestEventReporter test =
        testEventReporterFactory.createTestEventReporter(
            "custom-test", binaryResultsDirectory, htmlReportDirectory)) {
    test.started(Instant.now());
    test.metadata(Instant.now(), "engine", "custom");
    test.succeeded(Instant.now());
}
```

## Problems API producer data

`ProblemSpec.additionalData(...)` accepts arbitrary typed structured data
(since `8.14.0`). Define an interface extending `AdditionalData`; the model can
contain Provider API properties, bean-style fields, collections, and nested
objects:

```java
public interface SomeData extends AdditionalData {
    Property<String> getSome();
    List<String> getNames();
    void setNames(List<String> names);
}

problem.additionalData(SomeData.class, data -> {
    data.getSome().set("some");
    data.setNames(Collections.singletonList("moreData"));
});
```

Tooling API consumers retrieve this data with
`CustomAdditionalData.get(Class)`, passing a view interface that mirrors the
producer's model. This avoids string or JSON parsing:

```java
SomeDataView data =
    problem.getAdditionalData().get(SomeDataView.class);
String name = data.getName();
```

Run with `--warning-mode=all` to render relevant structured problems directly
in the console, including build locations, while retaining the link to the
HTML Problems report (since `9.3.0`):

```text
./gradlew test --warning-mode=all
```

## PMD report formats

An individual `Pmd` task can emit CSV, Code Climate, and SARIF reports (since
`9.4.0`). They are off by default and must be configured on the task rather
than the `pmd` extension:

```kotlin
tasks.pmdMain {
    reports {
        csv.required = true
        codeClimate.required = true
        sarif.required = true
    }
}
```

## Plugin validation

Applying `com.gradle.plugin-publish`, `ivy-publish`, or `maven-publish`
automatically enables stricter plugin validation (since `9.4.0`). Local plugins
in `buildSrc` and included builds are exempt. Other plugin projects can opt in:

```kotlin
tasks.validatePlugins {
    enableStricterValidation = true
}
```

`validatePlugins` reports targeted errors for invalid `@Optional` use (since
`9.6.1`):

- `@Optional` must accompany an input or output annotation.
- Do not combine `@Optional` with `@Internal`.
- Use only `@Internal` for an ignored property.

Correct the property model rather than suppressing the dedicated diagnostic.
