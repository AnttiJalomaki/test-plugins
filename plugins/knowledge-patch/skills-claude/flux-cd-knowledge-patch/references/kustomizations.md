# Kustomizations and reconciliation

## Custom health checks with CEL

Since 2.5.0, `Kustomization.spec.healthCheckExprs` can describe health for
custom resources that do not follow Kubernetes readiness conventions. Each
entry selects an API version and kind and provides failed and current
expressions:

```yaml
spec:
  wait: true
  healthCheckExprs:
    - apiVersion: cluster.x-k8s.io/v1beta1
      kind: Cluster
      failed: "status.conditions.filter(e, e.type == 'Ready').all(e, e.status == 'False')"
      current: "status.conditions.filter(e, e.type == 'Ready').all(e, e.status == 'True')"
```

With waiting enabled, dependent Kustomizations do not proceed until the custom
resources are current.

Since 2.9.0, CEL health expressions for Kustomizations and HelmReleases may
leave `kind` empty. One expression can therefore cover every resource kind in
an API group.

## Dependency readiness

Since 2.7.0, entries in `Kustomization.spec.dependsOn` and
`HelmRelease.spec.dependsOn` can use CEL expressions for extended dependency
readiness instead of relying only on the dependency's standard Ready
condition.

## Deletion policies

`Kustomization.spec.deletionPolicy` provides fine-grained garbage-collection
control (since 2.5.0).

The `WaitForTermination` value, added in 2.6.0, waits until all managed
resources have been deleted before allowing the Kustomization itself to be
deleted:

```yaml
spec:
  deletionPolicy: WaitForTermination
```

## Referenced configuration watches

Since 2.7.0, kustomize-, helm-, and notification-controller can reconcile
immediately when referenced configuration changes. For Kustomizations this
includes:

- `postBuild.substituteFrom`
- `decryption.secretRef`
- both kubeConfig references

For HelmReleases it includes `valuesFrom` and both kubeConfig references. For
Receivers it includes `secretRef`.

Opt in one referenced ConfigMap or Secret:

```yaml
metadata:
  labels:
    reconcile.fluxcd.io/watch: Enabled
```

Or configure a controller to watch all matching objects:

```text
--watch-configs-label-selector=owner!=helm
```

## SOPS decryption

- Since 2.5.0, SOPS decryption applies to Kubernetes Secrets generated by
  Kustomize components.
- Since 2.6.0, the opt-in `ObjectLevelWorkloadIdentity` feature gate permits
  per-object and per-tenant identity for Kustomization SOPS decryption through
  KMS services.
- Since 2.7.0, kustomize-controller can use centrally managed Age keys for
  global SOPS decryption.
- Since 2.9.0, kustomize-controller can decrypt SOPS secrets sealed with the
  Age post-quantum cipher.
- Since 2.9.0, OpenBao and HashiCorp Vault authentication can use Kubernetes
  Workload Identity, exchanging the ServiceAccount token instead of storing a
  long-lived Vault token.

## Health-check cancellation

Since 2.7.0, the kustomize-controller
`CancelHealthCheckOnNewRevision` feature gate cancels an in-progress health
check when a newer source revision arrives.

Since 2.8.0, the same opt-in gate also applies to helm-controller and reacts
to:

- a new source revision;
- a spec change;
- a referenced ConfigMap or Secret change;
- a manual reconciliation;
- a Receiver-triggered reconciliation.

A cancellation reports `HealthCheckCanceled` on the `Ready` condition. When
enabling the gate for helm-controller, also enable
`DefaultToRetryOnFailure`; the default no-retry configuration can otherwise
leave a release stuck.

## Kustomize processing and apply control

`Kustomization.spec.ignoreMissingComponents` allows absent Kustomize
components to be ignored (since 2.7.0).

Since 2.8.0, kustomize-controller supports custom server-side apply stages for
explicit resource-application ordering.

Since 2.9.0, `Kustomization.spec.ignore` excludes selected managed fields from
both drift detection and apply. Use it when another controller owns a field:

```yaml
spec:
  ignore:
    - target:
        kind: Deployment
      paths:
        - /spec/replicas
```
